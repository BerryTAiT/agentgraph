# Security policy

## Threat model

`agentgraph` is an R SDK over a C++20 engine for building LLM agent graphs. The
main risks it is designed around:

1. **Prompt injection / untrusted content.** Tool results, retrieved documents,
   and web pages can contain instructions the model might follow. Defenses:
   `detect_injection()`, `sanitize_untrusted()`, `fence_untrusted()`,
   `guard_messages()`, `guarded_tool()` (see `R/guard.R`). These are
   *heuristics* — they raise the cost of an attack but cannot catch every
   paraphrase or encoding. Combine them with least-privilege tools.
2. **Tool misuse.** Tools can read/write files, run code, query databases, and
   make HTTP requests. Defenses:
   - `tool_policy()` + `restrict_tool()` restrict path/URL arguments of custom
     R tools (`R/policy.R`).
   - `file_tools_policy()` (or the `AGENTGRAPH_FS_ALLOW` / `AGENTGRAPH_FS_DENY`
     environment variables) sandboxes the *native* `read_file`/`write_file`
     tools, which execute in-process and cannot be wrapped by `restrict_tool()`.
   - Human-in-the-loop `interrupt_node()` to gate sensitive tool calls.
3. **Data exfiltration.** Anything in the conversation can be sent to the LLM
   provider. Defenses: `pii_scrub()` / `provider_pii()` redact emails, API keys,
   private-key headers, JWTs, AWS secrets, SSNs, credit cards, phone numbers,
   and IPv4 addresses before requests leave the process.
4. **Credential exposure over the network.** API keys travel in request
   headers. Defenses: TLS is always verified (no bypass anywhere in the code),
   redirects are capped at 3, and HTTPS is never downgraded to HTTP (both the
   WinHTTP and libcurl backends).
5. **Local-process attacks on the tool server.** Custom R tool handlers run in
   a separate R process listening on a TCP port (base R server sockets bind all
   interfaces). Defense: every request must carry a random per-run auth token
   generated by the parent process.
6. **Abuse of served agents.** `serve_agent()` / `start_sse_server()` expose an
   agent over HTTP. Defenses: optional bearer auth (compared in constant time),
   naive per-process rate limiting (120 req/min on the authenticated
   endpoints), and refusal to bind a non-loopback interface without a token
   unless `allow_unauthenticated = TRUE`. **Always put these servers behind TLS
   and a real reverse proxy in production** — they are development conveniences,
   not hardened servers.

## Hardening checklist for production

- [ ] Set `file_tools_policy(allow = ...)` before registering file tools, or
      don't register `read_file`/`write_file` for untrusted agents.
- [ ] Wrap untrusted-content tools with `guarded_tool()` and/or call
      `guard_messages()` on tool results.
- [ ] Wrap custom tools with `restrict_tool(tool_policy(...))` to constrain
      paths and domains.
- [ ] Use `provider_pii()` (or `pii_scrub()`) when prompts may contain PII.
- [ ] Serve agents with an `auth_token` and behind TLS + a reverse proxy.
- [ ] Use `run(..., max_total_tokens =, max_cost_usd =)` as a budget kill
      switch against runaway loops.
- [ ] Keep API keys in environment variables (never in code or checkpoints);
      note that checkpoint files and `log_path` traces contain conversation
      content — protect or scrub them accordingly.

## Known limitations

- Injection/PII detection is regex-based and heuristic; it is not a guarantee.
- The serve/SSE rate limiter is per-process and naive (fixed window), not a
  substitute for a reverse proxy.
- `tool_code_exec()` executes arbitrary R code by design; only register it for
  trusted agents.

## Reporting a vulnerability

Please open a private security advisory on GitHub
(https://github.com/BerryTAiT/agentgraph/security/advisories/new) rather than a
public issue. Include a minimal reproduction. We aim to respond within 7 days.
